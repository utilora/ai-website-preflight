# Phase 05.5 — Public Launch Hardening

This document is the implementation standard for an approved hardening slice on top of Phase 05. It is not a product-feature phase.

## Goal and boundary

Prepare the existing AI Website Preflight service for public deployment on a roughly 1 GB RAM host by fixing confirmed security, stability, and leftover issues from the Phase 01–05 handover.

This phase does not add SEO tool pages, authentication, payments, AI APIs, dashboards, GitHub mutation, Agency features, or a durable external queue.

## In scope

1. Upgrade Next.js within the 15.5.x line to a patched release that addresses CVE-2025-66478 and later 15.5 security fixes.
2. Add a process-local scan queue with a conservative active-scan cap.
3. Add bounded IP and target-host rate limits on `POST /api/scans`.
4. Decode deterministic embedded IPv4 from IPv6 (NAT64, IPv4-compatible, 6to4, Teredo) and reuse the existing IPv4 BlockList.
5. Persist and return only allowlisted response headers needed for detection evidence.
6. Correct the health endpoint stage field.
7. Delete unused Phase 01 stubs if they have no runtime or test dependency.
8. Update stage documentation without claiming a durable queue.

## Out of scope / prohibited

- SEO free-tool pages
- Login, registration, OAuth, Stripe, payments, subscriptions
- AI APIs, including Grok, OpenAI, and Claude
- Dashboards, teams, Agency, browser extensions
- Redis, Kafka, RabbitMQ, BullMQ, Kubernetes
- Automatic GitHub modification, pull-request bots, or automatic deployment
- Recovery of `queued` / `running` scans after process restart

## Concurrency

- Keep the existing `queued → running → completed/failed` states.
- Default `MAX_ACTIVE_SCANS=1`, hard-capped at 4.
- Additional accepted scans remain `queued` until a slot is free.
- Completing or failing a scan must release the slot and start the next queued scan.
- Process restart still does not resume in-flight work.

## Rate limit

- Apply to `POST /api/scans` only.
- Limit by client IP and by target hostname.
- Return `429 Too Many Requests` with a bounded error body, never 500, when a limit is exceeded.
- Use TTL, periodic cleanup, and a maximum key count so the limiter cannot grow without bound.

## Acceptance

- [x] Next.js is on a patched 15.5.x release and lockfile is updated.
- [x] Active scans never exceed the configured cap; failed scans release the slot.
- [x] Over-limit scan creates return 429; allowed requests still create scans after TTL.
- [x] NAT64, IPv4-compatible, 6to4, and decodeable Teredo private embeddings are blocked; ordinary public IPv6 is not.
- [x] `Set-Cookie`, `Cookie`, `Authorization`, and `Proxy-Authorization` never appear in public scan JSON.
- [x] Detection still sees CSP, HSTS, X-Content-Type-Options, Referrer-Policy, frame controls, X-Robots-Tag, Content-Type, and Location when present.
- [x] Health reports the current phase.
- [x] Unused Phase 01 stubs are removed or justified.
- [x] README, AGENTS.md, and architecture/decision notes describe Phase 05.5 and keep the process-local queue limitation.
- [x] `npm ci`, lint, typecheck, test, and build pass.

## Completion

Report the hardening summary, designs, dependency upgrade, removed files, five validation results, known limitations, commit SHA, and git status. Then stop. Do not start Phase 06.
